# Design

## 体验目标

融合后的体验应让学习者感到自己在同一条学习路径中，而不是在“聊天工具”和“课堂生成器”之间跳转。每个首批入口都应说明：当前学习目标、正在发生的课堂动作、AI 是否正在生成/思考、学习者下一步能做什么，以及结果会保存到哪里。

## 当前视觉基线

- 两个上游均为 Next.js/React 应用，且都有国际化、设置页面、复杂交互组件和暗色模式相关能力。
- OpenMAIC 已覆盖课堂生成、场景回放、编辑、测验/PBL、音频与媒体；DeepTutor 已覆盖工作区、聊天、知识、学习与伙伴等界面。
- 当前没有统一 design token、公共组件库、统一导航或已批准的品牌规范。后续跨应用体验应先沿用选定宿主的视觉系统，除非专门 feature 批准统一设计系统。

## 融合规则

- 首先保持选定宿主的现有导航、排版、颜色、圆角、反馈和语言约定；跨应用组件应优先通过明确的边界呈现，不做难以维护的视觉仿制。
- 每个 AI 相关操作都要有明确、可理解的状态：未配置、准备中、生成中、等待外部服务、成功、部分成功、可重试失败、已取消和无权限。
- 课前 Fusion 的“课程语义可信”与“Learner 个性化证据充足”必须分开表达：画像为 `insufficient_data` 时，只要课程语义上下文可信，仍应明确展示 Fusion 已可用，而不能把它呈现为失败或自动切回普通课堂。普通课堂只能由用户明确选择，或在可信上下文无法建立/不可恢复故障时作为显式 non-Fusion 恢复；恢复后的课堂必须说明未使用 Fusion 个性化上下文。
- 用户必须能区分“课堂内容”“AI 建议/生成结果”“个人学习记录”和“外部工具结果”；不把未验证的模型输出伪装成确定事实或评分。
- 课堂内的进行状态、进度、题目结果、保存/同步状态和潜在数据丢失风险必须可见。涉及异步生成或回写时，提供取消、重试或恢复的可见入口（依具体 feature 适用）。
- 文案默认使用简体中文；新增可见字符串必须接入所选宿主的 i18n 机制，避免在组件中硬编码仅中文文本。翻译范围和回退策略由 feature 合同说明。

## 响应式与可访问性

- 以桌面学习和课堂编辑为首要目标，同时确保常见平板与窄屏设备能完成首个学习闭环；复杂编辑器可在 feature 中声明受支持的最小宽度与替代路径。
- 全部核心操作必须键盘可达，有可见焦点；自定义控件应提供名称、角色、状态和错误提示。
- 文字与非文字对比度、缩放、焦点顺序、动态更新和错误消息遵循 WCAG 2.2 AA 的相关要求；不能仅依颜色表达进度、正确性或失败。
- 图像、图表、白板、音频/语音和视频应按场景提供替代文本、字幕/文本摘要、控制方式或等效学习路径；AI 生成的替代内容要允许修订。
- 不能依赖自动播放音频、快速动效或拖拽作为完成任务的唯一方式；为动画/媒体提供暂停、静音、减少动效或键盘替代。

## 验收表达

UI feature 合同应写可观察结果，而非仅列实现组件。例如：

- 学习者看到课堂生成请求的当前状态，失败时能读到不会泄露密钥的原因并重试。
- 学习者完成课堂后，能确认哪些结果已保存/同步，哪些仍只在当前设备。
- 键盘用户和屏幕阅读器用户能进入课堂、完成首个互动并理解得分或下一步提示。

布局像素规格、组件清单和状态截图仅在该 feature 需要时放到 `details/design.md`，并在合同中引用。
