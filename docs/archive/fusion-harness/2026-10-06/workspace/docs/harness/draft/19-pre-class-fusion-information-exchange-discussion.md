# 课前 Fusion 信息交换：产品目的、信息边界与讨论范围

> 记录日期：2026-10-04；整理日期：2026-10-05。
>
> 本文承接 [18 — Context Consumption 语义模型](18-context-consumption-semantic-model.md)，整理课前 Fusion 的产品目的、整体信息交换流程和已确认的边界，作为后续逐段讨论的入口。它是设计草案，不是 Feature 合同、架构 SSOT、最终交换 schema 或实现授权。

## 一、文档目的与讨论范围

Context Consumption 的目标，是建立服务器侧的 operational contract：服务器能够证明，冻结教学语义成为某次大纲生成任务的正式设计输入，并由实际承担课程设计的生成路径执行。它不证明模型内部理解、attention、reasoning 或严格反事实因果。

为设计这条契约，需要先明确生成输入的来源：OpenMAIC 向 DeepTutor 提出什么请求，DeepTutor 返回什么课程解释和教学依据，以及哪些内容经过接受后形成 Frozen Context。本文围绕这些上游信息约定，确定产品目的与职责边界；具体交换清单尚待逐段讨论。

讨论分为两个阶段：

| 阶段 | 讨论内容 | 本文定位 |
|---|---|---|
| 课前信息交换 | 课程语义请求、课程解释与教学提案、接受与冻结的约定 | 当前重点；记录已确认方向，列出待讨论部分 |
| 生成消费契约 | Authorized Projection、Task Binding、Generator Execution、Attempt Lineage | 留到后面，本文只说明各自讨论什么 |

后续四个概念分别关注：

| 概念 | 后续需要讨论的内容 |
|---|---|
| Authorized Projection（授权投影） | 如何从合法 Frozen Context 派生适合生成的教学输入，保持必要语义并满足数据边界 |
| Task Binding（任务绑定） | 如何使教学输入成为某次正式大纲生成任务的一部分 |
| Generator Execution（生成器执行） | 如何证明实际承担课程设计的生成路径执行了该任务 |
| Attempt Lineage（生成尝试关联） | 如何关联上下文、投影、生成尝试、执行及其产出 |

这些概念是后续讨论框架，不是已逐项确认的最终契约。本文不决定投影必需语义、执行证据门槛、重试关联或最终 JSON。Recommended 未采用与投影省略的区别、Evaluation Focus 应进入哪些任务、是否需要设计处置记录或 generator 确认，以及超时和中断时的结论，均留待后续。

继续保留 `Receipt → Availability → Consumption` 的语义区分，以及 Consumption 与 Output Alignment 分开取证的方向。输出是否采用建议、满足要求或对齐，不直接替代消费证明；消费成立也不自动证明输出合格或学习有效。

## 二、产品目的与系统分工

OpenMAIC 本身能够根据用户输入的自由文本生成课堂。课前 Fusion 的目的，是在这一能力基础上，由 DeepTutor 帮助解释课程需求并提供教学依据，使 OpenMAIC 更准确地组织本次课堂。

已确认的产品方向是：

> 以 OpenMAIC 中用户本次自由文本为起点，由 DeepTutor 帮助解释课程需求并提供教学依据，增强 OpenMAIC 原有的课堂生成能力。当前不新增学习者信息采集，也不依赖尚未建设的课中、课后或独立交互入口；未来可以接入这些来源提供的相关学习者信息。

DeepTutor 的作用包括两个相关但不同的方面。第一，帮助明确本次需求，例如解释主题、目标、范围和不确定之处；第二，为实现这些需求提供教学依据，例如知识关联、必要前置关系、教学重点和安排建议。OpenMAIC 仍然负责把这些输入组织成自身支持的课堂大纲，并进一步生成内容与活动。

这里的“叠加”是需求解释与教学依据的整合，不是把两段文本机械拼接，也不是让 DeepTutor 直接决定组件、播放器行为或具体运行命令。需求解释、补充、澄清和提案接受的具体规则尚未定稿。

## 三、整体流程与信息交换清单

以下流程用于组织后续讨论，不是新 API、schema 或实现计划：

```text
OpenMAIC 中用户本次自由文本
    ↓
OpenMAIC 发出的课程语义请求
    ↓
DeepTutor 返回的课程解释与教学提案
    ↓
OpenMAIC 校验、接受并冻结上下文
    ↓
Authorized Projection                 ← 留到后面
    ↓
OpenMAIC 大纲生成任务
    ↓
课堂内容与活动生成
```

请求和提案是主要跨应用交换边界；冻结、投影和任务组装主要属于 OpenMAIC 服务端内部处理。平台组件、输出结构和运行能力由 OpenMAIC 提供，不需要全部复制进 Frozen Context，也不应交由 DeepTutor 决定。

| 讨论部分 | 需要形成的信息约定 | 当前状态 |
|---|---|---|
| OpenMAIC → DeepTutor：课程语义请求 | 当前意图、明确要求、缺失或不确定信息，以及允许解释和补充的范围 | 下一步首先讨论，清单未定 |
| DeepTutor → OpenMAIC：课程解释与教学提案 | 课程理解、目标、知识范围和教学依据；区分解释、新增建议与澄清问题 | 待讨论 |
| 提案 → Frozen Context：接受与冻结 | 哪些内容可接受，哪些冲突要处理；保留哪些来源、限制和请求关联 | 待讨论 |
| Frozen Context → 大纲生成任务 | 冻结语义如何成为适合生成的教学输入 | 后续讨论授权投影、任务绑定、生成器执行和生成尝试关联，见第一节 |

信息清单应优先区分用户明确要求、DeepTutor 对要求的解释和新增教学建议。例如用户要求“十分钟了解线性函数”，课程范围解释与“额外加入二次函数比较”不是同一种信息。后者不能仅因来自 DeepTutor，就被记成用户明确提出的需求；具体接受规则尚待讨论。

后续应逐项记录信息来源、语义作用、提供方、使用方、明确或推断状态，以及必要限制。这个整理维度是讨论工具，不是已批准的字段列表。

## 四、当前课程需求与学习者信息的关系

“当前课程需求”以用户本次自由文本为起点，可以经过解释或必要澄清形成，不意味着必须由 OpenMAIC 独立定完后，DeepTutor 才能参与。用户明确表达的内容、系统推断和未确定部分需要区分，具体形成与确认规则尚待设计。

受众回答“这节课面向谁来设计”，例如初中生或编程初学者。课程约束回答“在什么条件下完成本课”，例如时长、范围和语言。这些信息可以来自本次明确要求；缺失时是否澄清、是否允许默认设定，以及默认如何表达，尚未决定。

学习者相关信息回答“有哪些与当前课程有关的个体情况或证据，可以影响教学安排”。它可能影响前置激活、讲解重点、示范或练习，但不自动获得改写课程目标、受众或时长的权限。

两类信息可能交叠。例如课程假定学习者具备代数基础，而未来的学习者证据显示相关基础不足。这需要显式处理其关系，不能因为两者都描述先验水平就直接合并。具体冲突规则留待信息交换设计。

## 五、学习者信息的当前范围与未来来源

当前设计聚焦课前 Fusion，不建设学习者信息获取能力。未来的来源可以包括课中、课后 Fusion，也可以包括一个独立交互页面，让用户与 AI 交互，以获得相关需求或学习者信息。

当前讨论不能假定这些入口已经提供了完整学习者档案、历史目标或可靠掌握证据，也不能要求当前课前流程依赖它们才能成立。用户在本次自由文本中明确表达的背景或困难，仍属于当前可讨论的需求来源；它与通过长期学习过程积累的学习者信息应当区分。

没有学习者历史信息时，DeepTutor 仍然可以根据当前请求提供课程层面的分析和教学依据，但不能把一般性教学建议描述成根据该用户历史表现作出的个性化判断。未来各来源如何区分用户自述、系统推断和学习证据，以及这些信息如何被接受和使用，需要后续设计。

上述内容是当前产品讨论范围，不是对整个仓库既有能力的重新验收，也不改变历史 Feature 状态。课前不负责采集学习者信息，与课前未来能否使用已经获得的相关信息，是两个不同问题。

## 六、Frozen Context 的位置与职责

Frozen Context 不只是“DeepTutor 处理后的语义请求”。当前对象关系是：OpenMAIC 发出课程语义请求，DeepTutor 返回教学提案，OpenMAIC 服务端校验并冻结请求与提案，形成后续生成使用的语义快照。

当前代码中的 `FrozenLessonGenerationContext` 包含 `schemaVersion`、`contextId`、`semanticRequest`、`proposal`、`resolution` 和 `frozenAt`。其中请求保存课程输入，提案保存相应的课程解释和教学信息；其他内容承担版本、请求关联、解析状态和冻结时间等职责。这里的 Proposal 是经过契约解析的领域对象，不等于原始模型响应或内部推理轨迹。

因此，一项信息在生成任务中的作用，与它是否保存在 Frozen Context 中，是两个不同维度。受众和课程约束可以属于课程设计条件，同时作为请求的一部分被保存在快照中；学习者投影可以属于 DeepTutor 提案的一部分。不能把 Frozen Context 误解为只装 DeepTutor 增量信息的容器。

后续 Authorized Projection 将从这份冻结上下文派生适合生成的教学输入，再与 OpenMAIC 自己的能力和输出规则组成任务。它不负责重新获取需求或重新执行 DeepTutor 的课程分析。具体完整性规则留到后面讨论。

## 七、材料的职责与当前边界

材料处理没有被整体迁入 Frozen Context。Frozen Context 是语义快照，材料解析、存储和读取仍需由相应职责承担。

2026-10-04 的只读核对发现：普通 OpenMAIC 路径仍有材料正文、图片和搜索结果等生成输入；正式 Fusion 路径会拒绝浏览器提交的非空材料正文、图片和搜索上下文。初始正式请求构造中的 `sourceMaterialRefs` 当前为空数组。协议则约定材料默认交换服务端可验证引用、digest 和用途，正文传输需另行授权和最小化定义。

材料引用可以用于固定“本次依据哪份材料及哪个版本”，但引用存在不等于生成器已经取得可用正文；知识引用 ID 也不等于已经提供可用于教学的知识说明。材料具体如何解析、保存和供生成读取，应由相应职责承担。

这些是当前代码与协议的观察，不是材料迁移完成的验收结论。本期是否支持材料、交换引用还是内容、怎样建立受控读取路径，仍需单独确认。

## 八、后续讨论与阶段记录

下一轮从“OpenMAIC 发给 DeepTutor 的课程语义请求”开始，以本次自由文本为起点，先整理哪些是用户明确需求、哪些信息缺失或不确定，以及 DeepTutor 可以在什么范围内解释或补充。随后讨论提案返回的信息，再讨论接受与冻结的约定。

信息交换清单尚待逐段讨论，本文不直接推导最终 schema 或开始代码改动。材料的本期范围、缺失受众时的处理、系统推断与用户确认的关系，以及请求与提案的具体接受规则，均保留为后续问题。

用户已确认每个讨论部分结束后单独总结；讨论较长时，也可以中途记录局部共识。每份阶段记录需要保存目的、已确认规则、例子与反例、未决问题、对其他部分的依赖和下一轮入口。用户确认、agent 建议和候选方案必须分开，不为完成文档而提前定案。

上游信息约定稳定之后，再依次恢复四个概念的讨论，并最终检查整个生成契约是否一致。
